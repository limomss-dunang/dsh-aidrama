## 0. 结论先行

1. **这个赛道已经分成四种形态，不能混为一谈。** ①Agent Skill 包（drama-skills）；②可部署平台（LocalMiniDrama、火宝）；③桌面端多 Agent 工作台（kineo）；④真实生产工程（codex）。它们解决的不是同一个问题：①解决「知识怎么被 Agent 执行」，②解决「素材与任务怎么管」，③解决「多 Agent 怎么编排」，④解决「真跑起来会怎么翻车」。
2. **最值得抄的不是提示词，而是契约。** 连续性锁的「锁面逐字出现」、参考图的「REF/PLAN/待补/文生四态」、生产的「prepare→confirm 指纹」、规则的「rule_id + severity + 来源日期」、状态的「单一真相」、试错的「时间盒」。这些是花过钱、返过工才长出来的。
3. **「一句话全自动」是被高估的叙事。** 所有认真做的工具都有人工门：LocalMiniDrama 是 20/30 秒倒计时门，火宝是设置与任务确认，drama-skills 是 prepare→confirm，codex 是批次验收。把门去掉，等于把「重跑一次镜头」的钱交给模型决定。
4. **最被低估的是成本与返工。** codex 的 5 分钟预告片总成本 ¥3,106.85：模型会话 48.7%、I2V 34.4%、订阅 16.0%，而 334 张成功图只要 ¥26.42（0.9%）。I2V 生成 656 秒，最终剪入 401.12 秒，利用率 61.1%。**贵的是对话、试错和返工，不是出图。**
5. **状态多源是真实工程的第一杀手。** codex 同时存在 `shot_manifest`、`production_unit_manifest`、`review_status.csv`、`i2v_coverage_map` 四套状态，`manifest` 说 40 approved，`review_status.csv` 里 82 个 PU 是 79 pending / 3 approved，作者自己在 `AGENT_PROGRESS.md:225` 承认「以 CSV 为准」。插件的第一价值就是消灭这个。
6. **模型方言是硬约束，不是文风偏好。** 同一段剧情，Seedance 2.0 用「镜头 1/2/3」、Seedance 2.5 用整数秒时间戳与显式 `edit/extend` 参数、MiniMax H3 用三段/六段英文结构且首尾帧与参考互斥、Wan 3.0 又是另一种。套错不是「效果差一点」，是任务类型被误判、素材编号错位、声音凭空多出。
7. **最直接的先例不在用户清单里。** `zenstory-ai/oh-story-dsh` 已经把 drama-skills + 小说 + 游戏 + 视频解说打包成 DSH 插件，用 `shell.overlay` + portal 接管会话布局；它的「文件就是创作事实」「Skill provider + Role 子 Agent」非常成熟。本插件必须正面回答它，而不是重复造一个更差的它。
8. **空白点因此很明确：** 没有一个工具把「**结构化生产状态 + 可执行硬校验 + 模型方言编译 + 成本/时间盒台账**」放进 **DSH 原生会话视图**。oh-story 是「文件 + 技能」；LocalMiniDrama/火宝是「数据库 + 自建 SPA」；kineo 是「桌面端 + 多 Agent」。它们都不服务「Agent 与人在同一个会话里共编一个可校验的制片工程」。
9. **产品定位：会话旁的「制片台」，不是又一个「一句话生成器」。** 采用与生图/视频复刻一致的侧边栏入口 + 中栏工作台；Chat 与 Composer 仍是 DSH 原生的；结构化 `project.json` 是机器可校验的真相，Markdown 五件套是交付皮；每一步「能判定」的做成硬闸，「不能判定」的做成排队待办。
10. **MVP 只做前期制片 + 提示词编译 + 校验 + 台账**，不做视频渲染、不做 NLE、不做自动投流。这是投入产出比最高、也最不会和既有工具重复的一段。

## 2. 九个来源逐项拆解

### 2.1 zenstory-ai/drama-skills：把「文件系统」当数据库的短剧流水线

**定位（G2）**：不是生成器，而是 12 个 Agent Skill + 约 750KB Python 标准库脚本 + 5 个可选 HTTP adapter。创作判断由宿主模型的自然语言完成，脚本只做契约校验、索引、文件搬运、生产交接与剪辑渲染。

**真实完成度分三条链：**

| 链 | 结论 | 关键证据 |
|---|---|---|
| 文本链 | 可跑通 | 主校验器 2057 行、约 100 条错误分支；样例 EP001 校验 `OK` |
| 生产链 | 可跑通但有硬缺口 | 每次必须 prepare→人工确认→run；续接视频、`GROUP-*` 不能作为生产来源 |
| 剪辑链 | 可跑通但有环境依赖 | ffmpeg/ffprobe；画面文字只有 Remotion 一条路线 |

**量化**：20 个 skill 脚本、757 个测试方法、9 份 stage-contract 共 184 条带 ID 的分级规则（SHT 31 / VID 28 / SCR 24 / EDT 23 / CON 21 / AST 15 / REV 15 / IMG 14 / NVA 13）。

**六个最值得抄的设计：**

1. **五份文档分层，每份只对一种创作决定负责**：`剧本.md` 只写发生什么；`视觉设定.md` 只写跨镜不变的造型与锁定；`分镜.md` 写起点、唯一动作、终点；`图片提示词.md` / `视频提示词.md` 各自可复制。这比「一条大提示词」可维护得多。
2. **连续性锁（LOCK）把一致性降级成字符串包含**：`LOCK-XUTANG-SUIT《许棠深灰旧西装》（镜头：入画；图片提示词项：IMG-XUTANG-SHEET）· 锁面：dark-grey worn wool suit`。作用域（入画/全集/SHOT 列表）内，冻结关键帧、MOTION、被点名的 IMG 正文必须逐字包含锁面，由 validator 机械核对。**投入产出比最高的一条。**
3. **参考图四态互斥**：`REF-*`（文件在项目里，可投产）/ `PLAN-*`（图在创作者自己界面，按顺序挂，不可投产）/ `无（待补参考图）`（阻断）/ `无（明确选择文生视频）`（可投产但必须写静态视觉锚点）。用途是 9 值闭集：身份/造型状态/地理/构图/尺度/效果/起始帧/结束帧/风格。这同时是创作者语义和供应商 role 的翻译源。
4. **prepare→confirm 指纹**：确认串 `CONFIRM <job_id> <fingerprint 前12位>` 一次性消费；输入/输出/参数任一变化，旧确认立即失效；`run` 在启动 adapter **之前**消费确认，失败重试必须重新确认。**这是花钱操作唯一可接受的 UI 形态。**
5. **规则分级 + 规则 ID**：`structural_invariant / reviewed_invariant / craft_default / taste_option` 四级。UI 只对 structural 标红阻断，对 taste 不判错。这解决「AI 用统一配方压创作」的最大风险。
6. **`--partial` 渐进校验**：只核对已有文档，缺的规则「不算通过也不算失败」。每写完一份文档就能得到反馈，且不逼用户补造文件。

**坑（必须点名）：**

- README 徽章写 `Skills 11`，正文是 12——陈旧宣传件。
- `wan-3.0.md` 方言完整但没有 adapter，单看方言会误以为可直连。
- `evaluations/` 有完整盲评方法学，但仓库里没有任何跑分结果；「评估过」只能指方法可执行。
- `short-drama-review` 无脚本、无 selftest，是「审查知识包」而非「审查工具」，不能当发布门禁。
- 仓库同时保留已退役的 JSON 结构化层与当前 Markdown 层，两套互斥口径；第三方 Agent 枚举 `scripts/*_check.py` 会拿到矛盾结论。
- 单 SKILL 最大 22KB、H3 方言 22.7KB；弱模型一次灌入就丢字段。必须阶段化注入。
- examples/evaluations 的剧情文本版权归仓库所有者，不能搬；只能自造合成样例。

**对插件的启示**：契约要结构化、可校验；但不要把「五份 Markdown」当成唯一真相——那是为「Agent 直接读写文件」设计的。DSH 会话视图有数据库/JSON 的能力，应该把「机器要校验的字段」放结构，把「人要读的交付」导出为 Markdown。

### 2.2 xuanyustudio/LocalMiniDrama：最完整的中文短剧数据模型

**定位（G2）**：单机、单用户、无租户的 Express + SQLite + Vue3 平台；Electron 只是壳，在 Electron 主进程内 `require` 后端。约 28.7k 行后端 JS + 30.4k 行前端。

**真实完成度**：主链路（剧本→角色/场景/道具→分镜→图→视频→合成）真实可用；但「一键流水线」完全写在前端 `FilmCreate.vue`（443KB / 10,768 行），后端没有 pipeline 表、没有 job、没有调度器。

**数据模型（最值得抄）：**

- 17 张表；`storyboards` 49 列，覆盖叙事、镜头、生成、帧绑定、一致性、音频六组字段。
- `image_generations` / `video_generations` 双表；`task_id`（业务任务）与 `provider_task_id`（厂商任务）分离——**刷新/重启后续查的基础**。
- `characters` 有 6 层视觉锚点 JSON（`identity_anchors`）、多阶段造型（`stages`）、四视图、参考图、音色。
- `ai_model_map(scene_key → config_id + model_override)`：业务场景键到模型的间接层，让「某类任务用便宜模型」成为配置而非代码。
- `storyboard_image` 与 `image` 是两条独立配置（有参考图/无参考图），缺失时回退。

**六个可复用机制：**

1. **双 ID 任务模型** + 启动恢复：`pending/processing` 一律标失败；有 `provider_task_id` 的重新挂轮询；`POST /videos/:id/resume-poll` 复用旧 task id，不重新提交。
2. **`@图片N` 槽位单一真源**：场景优先，角色按 `storyboards.characters` JSON 顺序，再道具；拼提示词与组装 API 参考图数组共用同一个函数。顺序即语义。
3. **帧类型归一**：`bindFrame` 把 `storyboard_first/first`、`storyboard_last/tail/last_frame` 归一后分别写主图字段与尾帧字段，避免尾帧污染主图。
4. **流式增量入库**：长 JSON 每 ~400 字符尝试解析已完成对象并写库，进度写进任务；截断时带「已保存镜号 + 上一镜结尾」续写，去重合并，标记 `truncated:true` 仍算部分成功。
5. **视图状态进 metadata**：画布坐标、工作流组、当前步骤都写 `dramas.metadata`，不新建表。DSH 里对应把选中态/分组存会话 store。
6. **任务恢复三阈值**：后端 `updated_at` 10 分钟无变化=僵尸，本地 30 分钟=超时，前端同 taskId 轮询去重。

**坑（点名）：**

- 「素材不上云」不成立：默认把本地图片上传第三方图床 `imageproxy.zhongzhuan.chat`，`use_for_video: true`。
- 「失败自动重试每步 3 次」只对前端一键流水线成立；服务层对图片/视频没有重试。
- `/episodes/:id/characters/extract` 是桩，100ms 后返回空数组的「假成功」。
- 重生成分镜先软删整集旧分镜，失败不回滚。
- **零成本记账**；唯一相关调用指向不存在的 `cloudService`。
- ffmpeg 缺失时合成「成功」但 `merged_url` = 第一段视频（静默降级）。
- `ttsService.js:148` 明文打印 api_key；单机假设渗透全栈（无鉴权、CORS `*`、0.0.0.0）。
- 许可证 MIT，但复用代码要逐个文件确认没有对外部图床/中转站的隐式依赖。

**对插件的启示**：数据模型可以直接借鉴「项目-集-分镜-角色/场景/道具-生成记录」；但状态机、成本、鉴权、并发必须重做。前端「一键流水线」不能照搬——DSH 里应由宿主任务 + Agent 工具驱动。

### 2.3 Agions/kineo：一条真渲染管线，一层「多 Agent」包装

**定位（G1–G2）**：Tauri v2 + React 19 + Rust 的桌面端漫剧工坊，MIT，133 星，v0.0.2（README 写 v0.0.1）。约 436 个 `.ts` + 170 个 `.tsx`、89 个测试文件、6 个 Rust crate。它对外包装成 `ACS-2.0` 多智能体 DAG（`MasterDirectorAgent` + 6 个子 Agent + 黑板），但**语义层大半是规则而不是模型**。

**必须拆开看的两条管线：**

| 管线 | 位置 | 真实行为 |
|---|---|---|
| A 线（营销面） | `src/core/services/agent/*` | 6 个「子 Agent」全部不调用大模型：剧本解析是关键词/正则（`HierarchicalScriptParser.ts:89-259`），角色设定按索引取调色板（`CharacterDesignerAgent.ts:85-90`），分镜按 `idx % 5` 轮转运镜数组（`StoryboardArtistAgent.ts:84-86`），质检是四条写死基线分 90/88/92/95 加算术（`QualityAuditorAgent.ts:50,68,104,127`） |
| B 线（工程面） | `src/core/pipeline/step-*.ts` + `PipelineEngine` | 真正有 LLM 调用与 8 步流水线；`PipelineStep` 带 `retryPolicy / qualityGate / dependencies`，`pipeline-engine.ts:159-269` 有 Symbol context、checkpoint、pause/cancel、middleware |

**真渲染（这部分是真的）**：`src-tauri/src/services/video/manga_renderer.rs`（382 行）实现 9 种 `zoompan` 运镜（`punch_zoom` 前 15 帧 1.0→1.25、`breathing_micro` 正弦呼吸、`parallax_pan` 相位平移）、字幕 `force_style` 烧录、4 worker 并行、concat、BGM `stream_loop -1` + `amix`；编码器按 `h264_videotoolbox` / `h264_nvenc` / `libx264` 顺序探测。

**「声称 vs 实际」点名（这是本轮最重要的反例）：**

1. README「13 大 AI 提供商」：策略注册表只有 6 个真 provider + 1 个 mock（`provider-registry.ts:24-30`）；模型清单是硬编码常量表，UI 叫 `seedream-5.0`，实际发方舟的是 `doubao-seedream-4-0-250828`，返回对象又把 model 改写回 `seedream-5.0`（`providers/seedream.ts:25,31,48`）。
2. 「100% 本地 Keyring 加密」：`secure-storage-service.ts` 只是 Tauri Store 的 `secure-data.json`，全文 grep 不到 `keyring|encrypt|cipher|aes`，**密钥明文落盘**。
3. 「IP-Adapter 锁脸命中率 98%」：`ProjectBlackboard.ts:212` 的 `0.92` 与 `CharacterDesignerAgent.ts:129` 的 `0.98` 是硬编码数字，`<ip-adapter-plus:0.95>` 只是一句写进 prompt 的文本标签，API 请求里没有参考图。
4. 「自定义 Agent」：`CustomUserAgent.execute()` 只打一行日志「执行用户自定义 LLM 规则」，没有任何模型调用（`CustomUserAgent.ts:28-48`）。
5. 「4K GPU 压制」：只是 ffmpeg 输出尺寸 + 编码器探测；缺系统 ffmpeg 直接报错让用户去 `brew install`。
6. 无 Key 保底：`UnifiedImageGenerator.ts:169-186` 生成一张 SVG（画框、标题、`PROMPT:` 文本），却以 `image/png` + `.png` 落盘；ffmpeg 没有 SVG 解码器，这条「零门槛开箱即用」在渲染阶段极可能失败。
7. CSP 与真实调用不一致：`src-tauri/tauri.conf.json:33` 的 `connect-src` 不含方舟生图与 Bing TTS 域名，生产构建里这两条链路会被拦。
8. 分镜步骤 `step-storyboard.ts:59-64` 用 `Math.random()` 决定镜头数/景别/角度/时长。

**可抄的（只抄真的）：**

1. **黑板字段就是会话视图要投影的东西**：`stage`、`activeAgentId`、`dagNodes`（每节点 status/time/error）、`logs`、`approvalGates`、`subtitles`、`renderQueue`；`ProjectBlackboardStoreBridge` 做双向持久化。
2. **PipelineEngine 的 checkpoint/暂停/恢复**：按步骤 id 存取，恢复时用 `Object.assign` 重新挂 context；这是「刷新页面不丢」比前端内存队列更稳的做法。
3. **CinematicShotDecomposer 的纯规则分镜**：对白轮次 ≥2 时生成「双人全景建立 → 过肩正打/反打（按左右站位与 gaze 方向）→ 高张力插入反应特写」，锁定 180° 轴线；时长由台词字数推导（`CinematicShotDecomposer.ts:170-289`）。模型失败时可兜底。
4. **渲染配方**：9 种 zoompan + `force_style` 硬字幕 + 4 worker 并行 + BGM amix。适合做「会话内快速预览」，但 UI 必须把「预览」与「AI 成片」分开。

**不能抄的**：日志/文案里塞指标、随机数分镜、SVG 冒充 PNG、把 5 个 TTS 供应商做成 stub 仍列进 UI、明文 Key。

**对插件的启示**：多 Agent 编排不要自己造——DSH 已有 Agent、Subagent、Tool、Approval。插件只提供「制片领域的状态与工具」，把编排交回 DSH。真正值得借的是 **黑板字段、阶段机、checkpoint、审批门、规则分镜兜底、渲染配方**。

### 2.4 chatfire-AI/huobao-drama：真实的分镜=视频任务闭环，但不是「一句话到成片」

**定位（G1–G2）**：Hono + Drizzle + better-sqlite3 + Mastra 后端、Nuxt 3 SPA、Electron 37 桌面版；tag v4.0.10（2026-11-01）。**许可证 CC BY-NC-SA 4.0（禁止商用、衍生需同协议共享）**，GitHub 识别为 NOASSERTION——这是最重要的第一条。

**真实边界：**

- **不支持「一句话→成片」**：入口是「本集已有原文」文本框（`script-tools.ts:12-26`），只做「改写已有文本」，没有一句话扩写；四阶段（剧本/资产/视频/导出）各自独立，不自动串联（`episode.vue:2464-2495`）；没有自动质检、没有成本记账（3 处「计费」字样全是重生成前的确认文案）。「一键」只指批量补齐提示词、批量生成视频（带报价确认）、失败一键重试。
- **跑通的是「一个分镜段落 = 一次视频任务」**：系统提示词规定一个分镜 = 一个分镜段落 = 一次视频生成任务、8–15 秒、内部 2–4 个子镜头、不跨场景；给出时长公式（字数÷500 字/分钟、台词÷4.5 字/秒 + 2 秒余量）与「video_prompt 按 3 秒分段写」的规则（`workspace/prompts/storyboard_breaker.md:8,30-41`）。这天然适配 Seedance 4–15 秒限制。
- **参考图协议**：前端按 `[场景图, 角色图…, 道具图]` 顺序建索引，把 prompt 里的 `@名字` 替换成 `@图片N名字`，上限 9（Wan 3.0 为 10）。比在 prompt 里塞角色描述稳定。
- **工具写库 + 幂等 upsert**：`save_storyboards` 每批最多 8 段、首批 `replace_existing: true` 清空旧集、之后追加；按 `shot_number` upsert，重试不重复；`validateStoryboardBindings()` 校验 scene/character/prop 是否属于本剧，不属于直接抛错（`storyboard-tools.ts:72-105,262-336`）。
- **任务生命周期**：`sys_task` 一张表承载图/视频任务，`processing →（同步或异步轮询）→ 下载落盘 → 回写业务表`；轮询档位「图片 5s×120（≤10 分钟）、视频 10s×300」；进程内 `activeTasks`/`videoSubmissions` 防重入；启动时 `resumeInterruptedTasks()` 有上游 taskId 的续查、没有的判 `submission_unknown`。
- **下载安全**：流式写 `.part` → 校验 MP4 `ftyp` / WebM 魔数 → 原子 rename；超 512MB 拒绝；408/429/5xx 指数退避；错误信息脱敏 URL/Bearer/sk-/token。
- **适配器上限**：Seedance 前缀门禁、参考图≤9/视频≤3/音频≤3、有音频必须至少有 1 图或 1 视频、1080p 收敛 720p、时长夹到 4–15s；火山图片适配器不支持参考图，只用 prompt。

**可抄的设计：**

1. **数据模型四层**：`Project → Episode → Shot（段落=一次视频任务）→ Asset`，Shot 与 Scene/Character/Prop 用连接表；Shot 存 `duration / video_prompt / first_frame / last_frame / reference_images / status`。
2. **任务落库 + 启动恢复**：会话视图刷新/重启后还能显示「进行中」，靠的是 `sys_task`，不是前端内存。
3. **重新生成 = 新任务，且显式确认计费**：同分镜已有 running 拒绝提交；failed 需 `forceNew` 并提示「可能再次计费」；批量前弹「镜头数/总时长/模型/分辨率」确认。
4. **提示词资产文件化**：`workspace/prompts/<agent>.md` + frontmatter（`name/model`）+ 语言变体 + 代码兜底 + 设置页在线编辑。
5. **工具返回必须可校验**：写库后**回读数据库**判定成功（`video-prompts.ts:78-84`），不要相信模型说「已保存」。

**坑：**

- **CC BY-NC-SA 4.0，禁止商用**；只能读设计，不能搬 `episode.vue`、`ffmpeg-merge.ts`、适配器代码。
- 默认把 7 条推荐配置写成同一个商业中转站 `https://api.firemux.{cn|com}`，模型名由中转站定义，本地无法核实上游真实模型。
- 无成本记账、无自动质检；四阶段全手动。
- 密钥明文存 SQLite `ai_service_configs.api_key`，API 返回明文并回填设置页编辑表单。
- `docker-compose.yml` 挂 `/var/run/docker.sock` 并开 Watchtower HTTP API（默认 token `please-change-me`），仅适合自用。
- `episode.vue` 6239 行，轮询/参考图/批量/恢复与样式混在一起，直接借鉴会把技术债带进插件。

**对插件的启示**：Mastra 的四 Agent 分工可作「领域角色」参考，但 DSH 里应改成 Tool + Prompt 模板，不引入第二个 Agent 运行时；商业授权内容不能进插件。

### 2.5 codex 真实生产工程：钱与返工长什么样

**定位（G2 + 本机数据）**：一个人 + 一组 Agent，用 GPT-Image-2 出首帧、HappyHorse 做 I2V、FFmpeg 合成，把 5 分钟预告片从「风格不确定」推到「可发布」。21 天、¥3,106.85、44 剪辑镜、82 个生产单元、40/40 I2V approved、成片 337.42 秒。

**真实规模：**

| 维度 | 数字 |
|---|---|
| 首帧候选 | 175 张（52 个 PU，PU080 单点 33 版） |
| 锚点备份 | 23 个目录 |
| 现金 | ¥3,106.85（模型会话 48.7% + I2V 34.4% + 订阅 16.0% + 图 0.9%） |
| 人工 | 仅记录 265 分钟（未折算金额） |
| 利用率 | I2V 生成 656s → 剪入 401.12s = 61.1% |
| 每分钟成片 | ¥552.5（账单口径）/ ¥478.5（有效 I2V 分摊） |
| 结果 | 链路跑通，传播失败：四个平台几乎没有流量 |

**最重要的六个教训（按可产品化排序）：**

1. **单一状态机**：真实工程有三份状态打架。插件必须一镜一 PU 一记录，`status` 只存一处，其余视图全是投影。
2. **硬事实 YAML + lint 规则引擎**：规则带 `rule_id / severity / reason / 来源日期`，`build_pu_request()` 是唯一请求入口。20+ 条规则、error/warn 两档。这是把「跨 5 天被问 5 次」关掉的唯一办法。
3. **尺度必须绑可见参照物**：只写「3m」无效，模型会解释成房间穹顶/小光点/能量墙。必须写「直径 = 中央地垫长边 1.3–1.5 倍 ≈ 一层楼高，边缘不得包住沙发/木柜/厨房门洞」。这条对漫剧/科幻尤其关键。
4. **时间盒**：单 PU 候选 ≤5、墙钟 ≤90 分钟，到点强制选最优继续。SC02 27 张、SC08 21 张、PU080 33 版就是没有时间盒的代价。
5. **覆盖门禁前移**：I2V 强继承首帧——身份、服装、空间布局、花纹全部继承。13 个 PU 在 I2V 前被 `blocked-before-I2V` 拦下（服装漂移/身份不一致/花纹错误/空间错位）。**拦截点必须在首帧阶段，而不是视频阶段。**
6. **成本双口径**：记录口径 vs 后台账单口径并列；按阶段/模型/PU 拆；显示「失败免计费 / 订阅内 / 待补账」三态；自动算每分钟成片成本与素材利用率。81 条 I2V 行 `unit_price=0`，¥1,070 最后靠后台账单回填——这是反面教材。

**失败模式库（20 类，节选）：**

| 失败 | 真实证据 | 修复 | 可自动化 |
|---|---|---|---|
| 屏障尺度漂移 | 用户连问 3 次「3 米约束没用吗」 | 绑可见参照 + 统一强制句 + lint | 高 |
| 场景生成没接人物锚点 | 跨 5 天被问 5 次 | 唯一请求构建器强制解析 | 高 |
| 多张 base64 参考 → 空响应 | 54272 字节空响应/断连 | 合成单张 JPEG | 高 |
| 参考太重 → 照抄旧图 | SC02 反复 | 1 张轻参考，最多 2 张 | 中 |
| prompt 超长 | >5000 字符直接失败 | 控 150–400 词 | 高 |
| 儿童 + 灾难词被审核拦截 | 4 个端点全挂 | 词表软化 + 分级方案 | 半 |
| 整批盲跑无叙事 QA | B2 v1 十张整批 rejected/F | 先 1–2 张样张再扩批 | 高 |
| 状态双源不一致 | 79 pending vs 40 approved | 单一权威（尚未解决） | 高 |
| 字幕按理论时长排 | 到片尾偏 1.208s | ffprobe 实测时长驱动 | 高 |

**不适合自动化的部分**：风格是否锁定、叙事钩子与传播力、批次验收、剧情口径变更、inpaint 修哪一处、音乐情绪、移动端可读性终判。共同点：这些是「值不值得」的判断，不是「对不对」的校验。插件边界 = 可判定的做硬闸，不可判定的做排队待办。

### 2.6 AI 短剧提示词知识库：可执行协议，而不是模板大全

**定位（G2）**：10 个分区，覆盖剧本、角色/场景、分镜/动作、声音、题材、工具适配、质检、来源、同类对比、开源提示词工程；有 L1–L4、A–D、G0–G4 三套独立标签，`output_verified=false`、G4=0。

**五个可直接进插件的资产：**

1. **提示词分层模型**：L1 组件词 / L2 镜头模板 / L3 生产段落 / L4 可执行资产。L4 的判据是「有输入输出契约、有状态、有校验、有失败记录」，不是长度。插件里应把 L4 做成 schema + validator，把 L1/L2 做成可插入片段。
2. **角色 8+1 槽位 + LOOK 编号 + 四个 `[*_LOCK]` 块**：年龄性别/脸型五官/发型发色/体型身高/服装编号/配饰/气质/禁用项/光线基准。`lock_text` 由九槽渲染、只读；分镜只允许引用 ID；同义改写直接 error（「银灰色短发/灰发/银色短发/浅灰色头发」在模型眼里是四个人）。
3. **方言矩阵**：Seedance 2.0（镜头序号、`@图片N`）/ 2.5（整数秒时间戳、`{角色说：}`、`edit` 需 `ratio:adaptive`+`duration:-1`）/ H3（`<Picture N>`、`<d>[Chinese]</d>`、首尾帧与参考互斥、`N/A` 必须显式写）。插件必须先选模型、只读该方言、再填内容。
4. **质检/返修协议**：14 类失败枚举、补丁 schema、单变量 ledger、20/30 分制离线评分卡。返修补丁只换出错镜，不重写整场。
5. **题材模板**：9 类题材的冲突发动机、视觉符号、禁用装置、默认时长。插件里应做成 `genre_profile` 预设，而不是自由文本。

**知识库自己的缺口（必须继承其诚实）：**

- G4=0，全库无本机复现；唯一实测是 grok 中文人声孤证。
- 语速 3.8 / 2–2.5 / 4–6 字/秒三处口径未统一；单句 15 vs 20 字；镜头 3–8 / 4–8 / 4–10 秒。插件应做 `rate_profile` 枚举并分别校验，而不是选一个删掉其余。
- 「视觉身份证 9 项」与「8+1 槽位」同名不同物；姿态、表情范围、说话节奏在槽位里没有位置，必须外键到 `action_board` / `expression_board` / `voice_card`。
- Wan 3.0 方言未逐行读原文，Kling 无协议级来源；插件不得伪造「支持」。
- VO 三规则来自对「付费进阶版」的描述（G1），却被写成硬规则；使用强度超过证据强度。

### 2.7 第七轮 GitHub 台账：元调研揭示的生态真相

**方法**：Search API 命中 338 条 → 去重 267 仓库 → ≥100★ 98 个 → 人工核验 40 个左右 → 读到正文 8 个 → 第三方评测 2 个 → 本地实测 0 个。

**六个判断（本报告认可并沿用）：**

1. 形态在迁移：从「提示词列表」到「Skill 包 + 协议文件」。
2. 真正稀缺的不是 prompt 数量，而是证据链（原帖 + 日期 + 模型版本 + 复测 + 稳定度）。
3. 星数与贴题度弱相关：0★ 的 `someonerow-oss/ai-short-drama-prompts` 比很多千星仓库更懂中文短剧。
4. 最大增量在模型专项协议；这是「换模型就失效」的知识，必须单独立文件。
5. 授权比内容更容易踩坑：MIT/Apache 稳，CC BY-NC-ND 不能商用，NOASSERTION 默认保留所有权利。
6. 声音与字幕仍是洼地，但声音不是空白：音色设计有指南、音效/BGM 有提示词库、混音有工程规范，都藏在工具仓库的 `references/` 里。

**对插件的启示**：不要做「第 1001 个提示词库」；做「能校验、能追溯、能编译」的协议层。每个模板带 `evidence / verified_at / source_url`，UI 显示证据徽章。

### 2.8 oh-story-dsh：用户清单外、但最直接的先例

**定位（G2）**：MIT、v0.1.22（2026-11-03），DSH 社区插件，把小说、短剧、游戏、视频解说四套 Skill 打包进 DSH，加四个工作台。它不引入第二套 Agent 运行时或项目数据库；Agent、会话、模型、权限审批、Chat 全是 DSH 原生的。

**它怎么做的：**

- Host 注册 9 类贡献：4 个 Skill provider、`oh_story_role` 工具（走 DSH spawn）、只读参考工具、`oh_story_production` UI 意图工具、`tools/pre-execute`/`post-execute` 钩子（长篇细纲门禁、章节提取写围栏）、Session 级创意文件路由 + 游戏/视频预览路由。
- Browser 只注册两个官方 slot：`shell.overlay`（声明 Session 级三栏工作台座位）与 `tool.call.toolview`。
- 工作台不是无条件接管：只有当前 workspace 真的有创作项目时才接管；没有时插件完全不出现；「收起创作工作台」随时可退回原生会话，选择按 workspace 记住。
- 短剧工作台读每集最多五份 Markdown，投影成镜头板、素材板、任务/版本、成片顺序、无限关系画布；生图/生视频/配音/音乐先预览、确认后才调供应商 API。
- 它把「文件就是创作事实」贯彻到底：不建并行数据库；改哪份文件就是改哪一层决定。

**为什么它是必答题：**

- 它已经占了「DSH 里的短剧工作台」这个位置；如果本插件只是「又一个文件树 + 五份 md」，用户没有理由换。
- 它的「Skills + Roles + 文件协议 + 预执行钩子」非常成熟，值得学的是**边界与所有权**，不是 UI。
- 它暴露了三个可攻击的弱点：
  1. **强依赖宿主机 Python 3.9+/ffmpeg/环境变量 Key**，生图/生视频走外部 adapter；DSH 里已配置的模型不能直接用。
  2. **没有结构化生产状态**：五份 Markdown 是创作真相，但「镜 → PU → 覆盖 → 素材 → 成本」这些机器要算的东西没有一等公民；投影是只读的，校验靠解析 Markdown。
  3. **布局接管很重**：`shell.overlay` + `createPortal` + 手动测量/滚动/Composer 避让；升级 DSH 时是高风险面。

**本插件的差异化因此成立：**

| 维度 | oh-story-dsh | 本插件 |
|---|---|---|
| 形态 | 布局接管式工作台 | 侧边栏入口 + 中栏工作台（同生图/视频复刻） |
| 创作真相 | 五份 Markdown | 结构化 `project.json` + Markdown 导出 |
| 校验 | 解析 Markdown 的投影诊断 | 一等公民 validator（字段/引用/方言/成本） |
| 模型 | 宿主机环境变量 + Python adapter | DSH `llm` 服务 + 已配置 provider |
| 生产 | 外部脚本/供应商 adapter | 先做「任务单 + 台账」，生成后续接 |
| 成本 | 无 | 双口径台账 + 时间盒 |
| 依赖 | Python/ffmpeg/Node | 纯 Node/DSH 运行时 |

## 4. 反常识结论（不要被表面误导）

1. **星数不是质量，README 更不是。** 0★ 的 `someonerow-oss` 比千星仓库更懂中文短剧；17k★ 的火宝是 NC 授权；133★ 的 kineo 有真渲染管线，但「6 个子 Agent」全是规则、锁脸是硬编码 0.98、Keyring 是明文 JSON。选型看「契约是否可执行」，不看星，也不看宣传。
2. **「全自动」是去掉门的委婉说法。** 所有能用的工具都保留人工确认；真正的差异是「门放在哪、是否可解释、是否一次性」。把门做成倒计时（LocalMiniDrama）比做成审批弹窗更轻，但没有「改完再继续」的语义。
3. **提示词不是瓶颈，状态与契约才是。** 几千条 prompt 的仓库很多，能给出「字段 + 状态 + 校验 + 失败记录」的极少。插件应把预算花在 schema 和 validator 上。
4. **「本地」通常只指数据在本机。** LocalMiniDrama、火宝、kineo 的生成都调云端 API；真正全本地的只有 ComfyUI 一类，需要大显存。
5. **长提示词会压垮弱模型。** 22KB 的方言文件一次灌入，字段就开始丢。必须「先选模型 → 只读该方言 → 再填内容」，并且把可判定字段做成 schema。
6. **最贵的不是图。** ¥26 的图 vs ¥1,512 的模型会话；一次整批否决只烧 ¥0.8，却烧掉一天。成本面板必须按「阶段/模型/PU」拆，而不是只记「张数」。
7. **参考图越多不一定越稳。** 多张高细节参考会把模型拉回旧图/完整室内；54272 字节的空响应是参考过重的典型；1.9KB 的轻参考反而能过。
8. **状态多源比模型漂移更致命。** 模型漂移看得见，状态打架看不见；最后所有报表都不可信。
9. **模型方言是任务契约，不是文风。** 写错 `edit`/`reference` 会让 2.5 直接报任务类型不匹配；H3 首尾帧与参考互斥，拆开提交后面几段没有指代对象。
10. **「文件是真相」与「结构化状态」不是二选一。** 真相给谁用？Agent 读文件方便，机器校验结构方便。正确做法是：结构是机器真相，Markdown 是人的交付皮；导出时生成、导入时不反向解析（或只做一次性导入）。

## 5. 产品机会与定位

### 5.1 形态选择：从「会话视图」到「侧边栏工作台」

> 最终决定：按用户要求，采用与生图 / 视频复刻一致的**侧边栏「会话 / 短剧」入口 + 中栏工作台接管**，不注册 `conversation.view`。下面保留会话视图的对比，作为未来可切换的备选；已实现代码走的是侧边栏形态。

DSH 0.2.x 的 `conversation.view` 是官方 slot：注册一个 View，出现在会话头部的 View tab 行；Chat/Trajectory/Context/Fleet 是同级；Composer 仍保留。它天然满足四件事：

1. **Session 级作用域**：拿到 `sessionId`，可以绑定项目、记住选中集/镜、随会话切换恢复。
2. **不抢布局**：不需要 `shell.overlay` + portal + 手动测量；升级风险低。
3. **人与 Agent 共处**：用户在看制片台时，仍可在 Composer 里对 Agent 说话；Agent 的工具结果在同一条会话里。
4. **可按需出现**：没有项目时只显示空状态；有项目时显示工作台；不污染普通编程会话。

但它与生图/视频复刻的既有交互不一致，用户明确要求后两者那种「侧边栏入口 + 中栏接管」；因此最终实现用 DOM 接管，当前 sessionId 从 `[data-conversation-content][data-conversation-session]` 读取。

### 5.2 定位

> **会话里的 AI 短剧/漫剧制片台：把「剧本 → 资产 → 分镜 → 提示词 → 生产台账」变成可校验、可追溯、可协作的结构化工程，而不是一堆散落的提示词。**

三个关键词：

- **制片台（Production Desk）**：不是聊天玩具，是有阶段、有门禁、有台账的工作面。
- **可校验（Verifiable）**：每个字段、每条引用、每个方言规则都能被脚本判定；错误带 rule_id 和中文原因。
- **会话原生（Session-native）**：项目绑定会话，Agent 与用户共编；数据落在 workspace，可导出、可版本管理。

### 5.3 差异化（相对 oh-story-dsh 与其它）

1. **结构化状态 + 一等公民 validator**：不是解析 Markdown 的只读投影；字段可以编辑、可以校验、可以阻断。
2. **模型方言编译器**：选择目标模型后，从结构化镜头生成该方言的正确正文，并在提交前跑硬校验。
3. **DSH 原生模型**：文本走 `llm` 服务，后续图像/视频走已配置 provider 的接口；不需要 Python、不需要在启动前 export 一堆 Key。
4. **成本/时间盒台账**：每镜记录候选数、墙钟、模型、token/金额、失败原因；批次级预算。
5. **锚点体系产品化**：L1–L6、8+1 槽位、LOOK、状态链、尺度参照物、参考图预算器。
6. **Markdown 导出而不是 Markdown 真相**：与 drama-skills/oh-story 的生态兼容（导出五件套），但内部不被文件格式绑架。

### 5.4 非目标

- 不做「一句话全自动成片」；不做 NLE；不做投流；不做多租户；不做模型网关；不替代 DSH 的 Agent/审批/会话。
- v0.1 不调用图像/视频模型（只做任务单与台账），避免一上来就烧钱和踩上游协议。

### 6.6 UI 细节

- **空状态**：三步引导（起项目 → 生总纲 → 拆第一集），不从空白表单开始。
- **阶段导航**：显示每阶段「已填/总数」与门禁状态（灰/黄/红/绿）。
- **分镜表**：每行一镜，左侧镜号与状态点，中间核心字段，右侧校验徽章；点击展开右栏检查器。
- **提示词**：方言下拉 + 「编译」按钮 + 可复制正文 + 警告列表；正文按段着色（画面/动作/声音/锁）。
- **资产卡**：锁面只读展示，复制按钮；「锁定」后字段只读，改动需先解锁并记录 decision。
- **右栏**：「为什么拦我」列表（rule_id + 中文原因 + 定位到镜/字段）。
- **项目切换**：workspace 内多项目；新建/打开/导出；项目绑定 sessionId。

### 6.7 Host / Client 技术设计

**Host（Cordis 插件）**

- `inject: ['webServer']`；`ctx.get('llm')`、`ctx.get('systemPrompt')`、`ctx.get('tools')` 可选。
- 路由前缀 `/api/dsh-aidrama`：`config` / `projects` / `project` / `generate` / `compile` / `validate` / `export`。
- 存储：
  - 配置：`~/.dsh/storages/dsh-aidrama/config.json`（密钥不回读）。
  - 项目：`<workspace>/.dsh-aidrama/projects/<slug>/project.json`（原子写 + 版本号，防并发覆盖）。
  - 会话绑定：配置里的 `projectSessions: { [sessionId]: projectId }`。
- LLM：`llm.stream({ provider, model, system, messages, maxTokens })`；要求 JSON 输出，解析失败重试一次（带错误提示）。
- 安全：仅 loopback 路由（DSH webServer 已保证）；路径 containment；项目 id 白名单正则；导出目录限定在项目内。

**Client（React 18）**

- 侧边栏在「新会话」旁插入「会话 / 短剧」；点「短剧」后给 `<html>` 加 `data-aidrama-active`，中栏隐藏原生会话、显示 `[data-aidrama-view]`。与生图/视频复刻/评论插件通过 `dsh-panel-activate` 事件互斥。
- 当前 sessionId 从 `[data-conversation-content][data-conversation-session]` 读取，再调 `/api/dsh-aidrama/session` 解析 cwd；没有会话时显示空状态。
- 状态：组件内 `useState` + 服务端持久化；切回「会话」不卸载工作台，状态保留；切换会话后重新读取 sessionId 并载入绑定项目。
- 样式：注入 `<style>`，用 DSH CSS 变量（`--dsw-alias-*`）适配明暗；不引入 UI 框架。
- 失败策略：任何 DOM/接口错误只记录告警，不阻断 Web 启动（与 dsh-video-replica 一致）。

**Agent 工具（v0.1 至少 2 个）**

- `aidrama_status(projectId?)`：返回项目摘要、阶段门禁、下一步建议。
- `aidrama_generate(projectId, stage, instruction?)`：调用 LLM 生成某阶段，写回 project.json。
- 后续：`aidrama_update_shot`、`aidrama_compile`、`aidrama_validate`、`aidrama_export`。

## 8. 风险与合规

| 风险 | 说明 | 对策 |
|---|---|---|
| 模型方言漂移 | H3/Seedance 参数随版本变 | 方言做成数据文件，带 `verifiedAt/source`；UI 显示核对日期；规则可开关 |
| LLM JSON 不稳定 | 生成总纲/分镜可能缺字段 | schema 校验 + 一次修复重试 + 失败保留草稿 |
| 数据丢失 | 并发写/刷新 | 原子写 + revision 冲突检测 + 前端本地草稿 |
| 许可证 | 火宝 NC、部分仓库 NOASSERTION | 只学结构，不复制原文；插件 MIT；导出模板自写 |
| 内容合规 | 仿冒现实人物、暴力、未成年 | 内置 forbidden 清单与提示；导出前提醒；不做真人克隆 |
| 隐私 | 项目数据在 workspace | 不上传；生成走用户自己的 provider |
| DSH 升级 | 中栏 DOM 选择器 / 会话属性变化 | 只依赖 `data-pane`、`data-conversation-session` 等稳定属性；找不到就显示空状态，不影响原生会话 |
| 误以为「已验证」 | 本插件无 G4 实测 | UI 显示证据徽章；不宣称生成质量 |
