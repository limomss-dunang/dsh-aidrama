# 审查清单：找错不只找 bug，还要问“这个功能是否合理”

日期：2026-11-05
适用：dsh-aidrama 及类似生成式工作台的功能设计、真实测试、复盘。

## 1. 新增的必问项

以后每次找错、每次提功能，必须先过这一条：

> **这个功能本身合理吗？调研项目里是怎么做的？**

不是只问“代码有没有 bug”，而是先问：

1. 这是真实用户需求，还是为了绕开另一个 bug 临时加的？
2. 调研项目里有没有同类能力？它属于哪一层：模型内部、宿主服务、工作台 UI，还是 Agent？
3. 它是不是把本该程序/模型完成的事转嫁给用户？
4. 有没有更简单的替代：删掉、内部化、复用现有能力，或只做一个只读调试视图？
5. 它新增了哪些状态、门禁、成本和维护面？值不值得？
6. 它和现有数据契约、阶段职责、门禁是否一致？

**如果调研里没有先例，默认先不做，先论证，而不是先实现。**

## 2. 本次真实测试中，用这条会提前发现的问题

| 功能/做法 | 是否合理 | 调研先例 | 正确做法 |
|---|---|---|---|
| 用户可见的「剧本理解」确认页 | 不合理 | drama-skills / LocalMiniDrama / huobao / codex 都没有让用户确认“角色是男是女” | 内部解析事实；用户只看角色/场景/分镜成品 |
| 性别标“未知”让用户填 | 不合理 | 没有项目这么做 | 模型+称谓/代词/身份词抽取；不能判断就报解析失败，不转嫁用户 |
| 按“钦犯”身份写囚服 | 不合理 | drama-skills 把“本集造型”单列；LocalMiniDrama 的 identity_anchors 先剔除服装 | 身份/服装分离；只认剧本明写，未写明用中性默认并标“未明写” |
| 从总纲生成全局角色/场景 | 不合理 | drama-skills 先 write 再 assets；LocalMiniDrama/huobao 从本集 script 提取 | 每集剧本 → 本集资产；全局只做去重合并 |
| 一键自动生图/生视频 | 不合理 | LocalMiniDrama 有 20/30s 人工门；huobao 四阶段手动推进；codex lint 不过不出图 | 文本/资产/分镜逐阶段验收，媒体最后 |
| 所有文本阶段共用一个 flash 模型 | 不合理 | LocalMiniDrama 有 `ai_model_map` 按 `role_extraction/scene_extraction/storyboard_extraction` 路由 | 解析/创作/分镜/校验分模型，质量优先的用强模型 |
| 0 error 就宣布通过 | 不合理 | drama-skills 有视觉设定与锁面；codex 有 story_facts/lint | 结构校验之外，增加原剧本事实对照 |

## 3. 四层找错法

### 第一层：功能是否该存在

- 用户真的需要这个按钮/阶段/字段吗？
- 调研里同类问题怎么解决？
- 这是产品能力，还是内部实现细节？
- 删掉它会损失什么？保留它增加什么认知负担？

### 第二层：职责是否放对

- 解析错误应该由解析器修，不是让用户确认；
- 创作决策才交给用户；
- 机械校验由 validator；
- 付费/长时间任务由宿主任务系统；
- 不要让 UI 承担本应自动化的判断。

### 第三层：实现是否正确

- 数据契约、状态、错误路径；
- 真实模型输出，不是 mock；
- 边界：空、长、截断、超时、并发、路径。

### 第四层：结果是否可验收

- 和原剧本逐项对照；
- 抽 1 个角色、1 个场景、1 个分镜、1 张图、1 条视频；
- 写明哪些是事实、哪些是推断、哪些未验证。

## 4. 功能提案模板（以后先写再写代码）

```md
## 功能：xxx

### 用户需求
谁在什么场景下需要它？

### 调研先例
- 项目/文件/行号：
- 它放在哪一层：
- 它解决什么问题：

### 归属
这是解析器 / 生成器 / 宿主 / UI / Agent 的职责？

### 最小方案
不新增 UI/状态的情况下能不能做？删掉/内部化是否更好？

### 门禁与成本
失败时怎么办？会不会调用付费模型？用户需要确认什么？

### 验收
用哪些原剧本事实、哪些样本、哪些文件证明它对了？
```

## 5. 结论

“代码有没有 bug”是第四层问题。  
前三层是：

1. 这个功能该不该有；
2. 它该放在哪一层；
3. 它是不是把系统该做的事推给了用户。

这次「剧本理解」页、性别“未知”、囚服、从总纲生成资产、自动生媒体，都是前三层就错了，不是代码层 bug。
